Three Approaches for GBCR Mobile App

Field-focused Expo app — Inspections, AI Chat, Push Notifications

A

Monorepo — Shared Code

Add Expo app inside the existing gbcr-platform repo using a monorepo structure (Turborepo or npm workspaces). Share TypeScript types, API client, and utilities between web and mobile.

Pros

  • Single repo — shared types, no drift
  • Reuse existing API route definitions
  • One CI/CD pipeline to manage
  • Easy to keep web + mobile in sync

Cons

  • Repo gets larger and more complex
  • Build tooling needs monorepo setup
  • Web deploys could be affected by mobile changes
B

Separate Repo — Independent App

New standalone Expo repo that consumes the existing Next.js API. Copy shared types via a package or manual sync. Fully independent deployments.

Pros

  • Clean separation — no impact on web app
  • Independent release cycles
  • Simpler repo structure
  • Can hand off to separate team

Cons

  • Type definitions can drift between repos
  • API changes need manual coordination
  • Duplicate some shared logic
C

Expo in Subfolder — Lightweight Integration

Add an /mobile folder to the existing repo without full monorepo tooling. Import shared types directly via relative paths. Simple and pragmatic.

Pros

  • Simplest setup — no monorepo tooling
  • Direct access to shared types
  • Single repo, easy to navigate
  • Good for small teams

Cons

  • No workspace isolation — dependency conflicts possible
  • Less scalable long-term
  • Expo and Next.js dependencies may clash

Recommendation: Option A — Monorepo

For a project where both web and mobile hit the same APIs and share the same data models, a monorepo keeps everything in sync. Turborepo makes the setup lightweight, and you avoid type drift between codebases. The complexity cost is manageable for a team working on both platforms.
